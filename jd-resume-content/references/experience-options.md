# 逐段备选与取舍

在读完整段经历原文与 JD 后使用。目标是先把每段经历的潜力写出来，再决定它在最终简历中的位置。不要把这一步做成关键词表或“匹配／不匹配”的打分。

## 先找真实切口

1. 在 JD 中找与这段经历确有交集的具体工作、技术、场景或成果。回到原文，确认候选人做了什么、做到了哪一步。单有相同名词而无实际动作，不构成切口。
2. 想两到三种不同的阅读路线，再写正文。可变的是**先展示哪一面、用什么模块、从何处进入**，不是改造事实。例如技术项目可突出 JD 点名的 Skill System 及其他真实组件，也可突出系统解决的问题和关键设计；业务项目可突出转化链路、方案迭代或跨方落地。
3. 每个方案都给出可直接比较的标题、开头和完整要点。保留该路线所需的原始背景、本人职责、重要方法、数据及结果。不同方案可以详略不同，但不能只换模块名、抽掉关键事实后形成空壳。

## 何时先问

遇到原文已提及、且答案可能改变重点方案的作品、技术、成果或个人责任，但缺少关键细节时，先问具体问题。例如原文只说“用 Codex 做过个人项目”，而 JD 看重可运行 Demo，就问做了什么、本人实现了哪些部分、目前能否运行；不把这条直接删成“会用 Codex”。原文信息已足够支撑方案时直接写，不为每项 JD 加分条件发问。把同一经历的关键问题集中提出，不重新采访整个经历库。

## 方案呈现与用户选择

逐段呈现：**原经历名 → 对口切口 → 方案 A／B／C 的实际正文 → 各方案突出什么 → 推荐方案及理由**。只有两种确实不同且有依据的路线时给两种；原文经过定向提问后仍只够一种可信写法时，展示这一种并说明限制，不为凑数改写同一句话。用户可选一个、组合或提出新方向。候选方案供选择，不作为最终简历文件。

全部经历的备选都写完后，再建议：独立经历、并入身份或技能、与其他条目合并、或不放。独立呈现的经历要让读者读懂场景、本人角色、做法与产物或结果；只有身份和笼统职责时，先看能否补问，仍无内容则不单列。取舍说明放在方案讨论中，最终简历正文只留下选定内容。

## 避免空洞的写法

- “线上结果”“复盘沉淀”等孤立标签若只剩一个数字或一句话，把结果和导致它的做法写在一起。
- 同一项目的模块尽量使用一条主轴；若 JD 特别重视某项真实技术，可单列该技术模块并前置，不必遵循原项目的叙述顺序。
- 要点要交代行动发生的场景或目标、本人采用的方法、形成的产物或结果；已由条目开头交代的背景不必逐条重复。写成自然完整的简历语句，不机械拼接“问题／行动／结果”栏目。
- 原文没有数字时可写实际交付、采用、运行或协作状态；不补造收益，也不在正文写“未量化”。
