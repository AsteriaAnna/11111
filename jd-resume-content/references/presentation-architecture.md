# 呈现架构：身份、项目分量与职责地图

仅在身份定位难写、一个项目含多个工作模块，或同一经历在不同 JD 中可能有不同用途时读取。目标是设计阅读顺序，不是增加栏目数量。

## 1. “我是谁”先于经历列表

先问：目标读者看完第一屏，应记住候选人的哪一个可核实身份、哪两项实力？从经历库选择身份与证据，而非从 JD 复制理想人选。可用一句定位加一至两项支持信息；毕业年份、作品或 GitHub 链接、开源贡献、专业称号等，只有资料提供且内容可供查看或追问时才写。年龄不是默认简历字段，只有用户提供且认为与该投递场景有关时考虑。职位、校园大使等身份按正式名称和实际工作范围使用；挂名不暗示实绩。

如果主项目已经在开头清晰地证明定位，不另加重复的“核心能力”栏目。若证据分散，可以用短的“岗位相关亮点”把能力与来源连起来。

## 2. 用事实建立项目分量，再界定个人角色

重点经历的阅读顺序通常是：

1. 项目解决的问题、服务对象、交付物或已知规模；
2. 本人的身份、负责范围和协作对象；
3. 关键模块中的判断、实现、验证与结果。

先写项目分量，是为了让读者理解工作的价值；必须紧接个人角色，避免读者把团队或平台整体成果归给个人。对没有已知成果的项目，不为追求气势虚构市场规模、用户量或技术难度。普通工作也不必强制加一段项目背景。

## 3. 把复杂项目整理成可追问的职责地图

从经历库提取真实工作片段，再选择与 JD 最相关的拆分轴：**模块**（如检索、评估、接口）、**流程**（如获客、注册、激活）、**阶段**（如调研、实现、上线）、或**技能/决策**（如方案取舍、跨方协调、效果验证）。同一项目优先用一种主轴，避免多个轴交叉造成重复。

每个模块写出：做了什么 → 为什么这样做或如何实现 → 可观察的产物/结果。模块名应是读者可以提问、候选人可以回答的入口。没有足够动作或产物的模块不要单独成节；不要把工具名清单冒充职责地图。

## 4. 一个经历可有不同用途

对同一事实可安排不同位置：

- **主项目：**直接证明 JD 核心任务，有足够过程、结果与个人贡献可展开；
- **辅助经历：**证明可迁移能力，在其他经历中用一条说明；
- **身份/兴趣信号：**只有真实身份、接触或关注，适合定位、技能或末尾一句，不能代替工作成果；
- **暂不使用：**没有相应证据、重复或会误导读者。

例如扣子校园推广对增长岗可作主项目，拆为渠道引流、注册转化和线下联动；对 AI 产品岗若 JD 主要要求 PRD 与代码 Demo，它更适合作为用户路径观察的辅助证据或真实 AI 产品接触的身份信号，不应顶替未有的 PRD/开发项目。

## 5. 描述性标题的改写边界

可在正式名称旁加准确的描述性标题，优先露出岗位相关的技术、对象或成果。只有真的设计或使用了 RAG，且能解释检索对象、知识来源、生成链路和本人实现范围，才可把“智能问答助手”写成“基于 RAG 的智能问答助手”。只调用现成问答服务或仅学习过 RAG，不能这样改名。公司、职位、产品的正式名称不改。

## 6. 交付前用面试问题反测

只看定位、项目标题和模块名，读者会问什么？候选人能否用经历库讲清本人的输入、决定、产物、验证和边界？如果标题比故事强，降级标题；如果好故事被泛称埋住，把真实技术或问题前置。这个检查适用于产品、技术、增长及其他岗位。
